# Doro：Coding + PHM 统一智能体项目经历与面试指南

> 适用范围：简历项目经历、作品集项目页、面试自我介绍和现场演示。本文只使用当前
> 仓库能够验证的实现与指标，不继承旧项目中无法由本代码证明的业务数据。

## 一、先给结论：这个项目应该怎样定位

推荐把当前仓库描述为一个项目，而不是“Coding Agent”和“C-MAPSS 模型”两个互不
相关的 Demo：

> **Doro 是一个面向软件工程与工业健康管理的可扩展本地智能体。** 它以 Python
> 多轮 Tool Calling、权限、Skill、MCP、会话和上下文管理为统一底座，在 Coding
> 场景中执行代码检索、修改和验证，在 PHM 场景中编排确定性的 RUL 模型、异步训练
> Worker 与模型版本生命周期。

这个定位有三层价值：

1. **Agent 平台能力**：模型不只回答问题，而是调用工具完成有状态任务；
2. **Coding 执行闭环**：读取仓库、修改文件、运行命令、验证测试并回传证据；
3. **PHM 垂直验证**：证明相同扩展协议可以承载本地深度学习、长耗时任务和有风险的
   模型状态变更，而不是只能包装普通 HTTP API。

不建议只写“工业装备健康管理 Agent”。这个名称会隐藏 Doro 的通用底座，让项目看起来
像一个给 LSTM/Transformer 套上聊天入口的垂直 Demo。

### 3.4 极简版：两条 bullet

- 重构支持 2 类模型后端、Tool Calling、5 种权限模式、Skill/MCP、会话和子 Agent
  的 Python 本地 Coding Agent，打通仓库检索、代码修改、Shell/Git 与测试闭环；
- 将 FD001、LSTM/Transformer 和 SQLite 异步 Worker 接入同一运行时，以 6 个只读
  工具、10 个管理工具和候选发布/回滚实现可验证的 PHM 模型生命周期。

### 3.5 关于模型指标的两种写法

偏 Agent 或平台岗位时，可以不写模型精度，把有限篇幅留给权限、MCP、异步任务和
验证闭环。偏算法或工业智能岗位时，再加入：

```text
LSTM v1：测试 RMSE 15.16、MAE 11.42
Transformer v1：测试 RMSE 15.44、MAE 11.89、NASA Score 432.39
```

不要写“准确率 95%”：RUL 是回归任务。也不要写“Transformer 全面优于 LSTM”：
当前 LSTM 的测试 RMSE/MAE 更好，而 Transformer 的测试 NASA Score 略好。

## 四、按目标岗位调整重点

### 4.1 AI Agent / 大模型应用岗

- 设计兼容 2 类 LLM API 的多轮 Tool Calling 运行时，以 5 种权限模式统一管理工具、
  上下文、会话和子 Agent；通过 Skill 将自然语言意图转换为可审计执行流程；
- 实现 stdio 与 HTTP/SSE MCP 客户端，把 Coding 工具及 16 个 PHM 工具接入同一
  Agent；通过 Server 级 `readOnly` 声明控制计划模式准入和只读调用并行；
- 面向长耗时训练设计“管理 MCP 入队—SQLite 持久化—独立 Worker 执行—候选发布”
  控制面，以 5 秒心跳和 300 秒空闲退出管理单实例 Worker 生命周期。

### 4.2 Coding Agent / 软件工程岗

- 构建仓库理解、文件修改、Shell/Git 和测试验证闭环，配套计划模式、权限规则、错误
  回传、会话恢复和上下文压缩，以 234 项测试覆盖核心 Agent 行为；
- 将 MCP 与 Skill 作为领域扩展接口，使 PHM 的 PyTorch 依赖和任务状态不侵入 Agent
  主循环，并通过独立环境降低通用运行时与领域依赖耦合；
- 围绕子进程退出、MCP 超时、HTTP/SSE 会话、并发只读调用和权限拒绝设计测试，强调
  Agent 工程不仅是 Prompt，还包括协议、状态和失败路径。

### 4.3 工业智能 / 算法工程岗

- 在 FD001 的 100 台训练发动机上按设备完成 80/20 切分，仅使用训练设备拟合特征和
  标准化统计量，生成 30 周期窗口并限制 RUL 上限为 125，规避重叠窗口数据泄漏；
- 实现 57,665 参数的两层 LSTM 和 70,593 参数的两层 Transformer，在相同数据、
  batch size 128、学习率 0.001、seed 42 与早停规则下进行可复现比较；
- 将模型质检、预测、比较、指标和退化证据封装为确定性 MCP 工具，使用版本注册表、
  五项候选产物校验和回滚机制补齐算法从实验到 Agent 服务的工程链路。

### 4.4 平台 / 后端工程岗

- 以 SQLite 状态机实现 queued、running、cancelling、succeeded、failed、cancelled
  等任务状态，支持持久化参数来源、进度、错误、候选路径和 Worker PID；
- 使用全局租约、心跳线程和幂等 Supervisor 防止同一运行目录重复拉起 Worker，并让
  队列空闲后自动释放进程；
- 使用临时候选目录、五项产物验证、`os.replace` 和活动版本历史实现可恢复的模型发布
  流程，同时保持训练期间旧活动版本可继续推理。

## 五、架构：为什么它是融合项目

```text
                           Doro Agent Core
用户 ─→ LLM ─→ 多轮工具循环 / 权限 / 会话 / 上下文 / Skill / MCP
                         │                         │
                         │                         ├─ phm：6 个只读工具
                         │                         │    └─ 质检 / 推理 / 比较 / 指标 / 证据
                         │                         │
                         │                         └─ phm-admin：10 个管理工具
                         │                              └─ SQLite 队列 / Worker / 发布 / 回滚
                         │
                         └─ Coding 工具
                              └─ 文件 / 搜索 / Shell / Git / Web / 测试
```

Coding 和 PHM 解决的是同一个核心问题：LLM 不应该凭语言生成结果来冒充确定性执行。

- 代码是否修改，要以文件差异和测试结果为证据；
- RUL 数值是否产生，要以本地模型推理输出为证据；
- 训练是否完成，要以 Worker、epoch 进度和候选产物为证据；
- 模型是否发布，要以活动版本注册表的真实状态为证据。

PHM 因此不是 Doro 旁边的脚本，而是对 Agent 扩展边界的一次压力测试：它同时引入
重型依赖、确定性算法、长耗时任务、持久化状态和高风险写操作。

## 六、关键技术设计与取舍

### 6.1 LLM 编排，确定性工具计算

LSTM/Transformer 并不需要 LLM 才能预测。LLM 的作用是理解自然语言中的设备、模型
和操作意图，选择正确工具，按“先质检、后推理、再解释”的顺序组织结果。数值始终由
本地 PyTorch 模型计算，避免大模型直接编造 RUL。

### 6.2 为什么使用 MCP，而不是在 Agent 中直接 import PyTorch

MCP 提供三个工程边界：

1. **依赖边界**：Doro 主环境不需要安装 PHM 的 PyTorch 依赖；
2. **协议边界**：工具名、输入 Schema、错误和超时通过 JSON-RPC 暴露；
3. **权限边界**：只读推理与写管理服务可以分别配置、启用和审计。

这也意味着 PHM 服务可以被其他兼容 MCP 的客户端复用，而不是绑定在 Doro 的 Python
进程内部。

### 6.3 为什么分离 `phm` 与 `phm-admin`

`phm` 提供 6 个只读工具：模型列表、设备检查、RUL 预测、双模型比较、指标查询和
退化趋势证据。`phm-admin` 提供 10 个管理工具：提交训练、确保/查询/停止 Worker、
查询/列出/取消任务、发布、回滚和读取控制状态。

分离的收益是：

- 日常分析可以只启用 `phm`，不暴露任何模型状态修改入口；
- Doro 的 plan 模式会拒绝未声明只读的 MCP 工具；
- 只读工具可以与其他安全读取并发执行；
- 管理操作有独立的权限和审计入口。

需要准确说明：`.mcp.json` 中的 `readOnly: true` 是操作者对整个 Server 的信任声明，
Doro 据此进行计划模式和并发调度；它不会自动分析或证明服务端代码绝对没有副作用。

### 6.4 为什么训练放到独立 Worker

PyTorch 训练时间远长于一次 MCP 请求，直接在工具调用中训练会阻塞对话并触发超时。
当前链路为：

```text
Agent / CLI 提交
    → 管理服务校验参数并写入 SQLite
    → Supervisor 自动启动或复用 Worker
    → Worker 领取任务并持续回写 epoch 进度
    → 训练成功后保存到 candidates/
    → 用户检查后发布到正式版本目录
```

Worker 默认每 5 秒写入心跳，队列空闲 300 秒后退出。任务在 SQLite 中持久化，关闭
Doro 不会删除 queued 任务；后续 Worker 启动后会继续领取。当前没有 checkpoint
断点续训，被强制终止的 running 任务会在恢复流程中记录为失败，而不是伪装成继续训练。

### 6.5 为什么训练成功后不自动发布

“训练成功”只表示程序产出了候选文件，不表示质量适合成为活动模型。发布前至少需要
检查模型/版本、数据配置、验证集指标、是否只是 1 epoch smoke，以及以下五项产物：

```text
model.pt
config.json
metrics.json
history.json
residual_quantiles.json
```

发布会校验候选路径、模型名、版本和文件完整性，然后复制到临时正式目录，使用
`os.replace` 完成同文件系统内的原子重命名，并更新 `registry.json`。原活动版本进入
历史栈，可通过回滚恢复。

这里不能过度承诺：发布/回滚确认目前主要由 `/phm-training` Skill 与 Doro 权限策略
约束；`phm-admin` CLI 和管理服务尚未实现不可绕过的服务端审批令牌。生产化时还需
增加操作者身份、审批记录和不可变审计事件。

### 6.6 为什么按发动机 ID 切分数据

同一发动机相邻时间窗口高度重叠。如果先生成窗口再随机切分，同一设备的相似窗口会
同时进入训练和验证，导致指标虚高。当前实现先把 100 台训练发动机按 seed 42 划为
80 台训练、20 台验证，只在训练发动机上拟合特征选择、均值和标准差，再分别生成窗口。

训练轨迹为每个可用终点生成 30 周期窗口；官方测试集则为每台发动机取最后 30 个周期，
与 `RUL_FD001.txt` 的真实剩余寿命配对。

### 6.7 为什么同时实现 LSTM 和 Transformer

- LSTM 是参数规模小、训练稳定、适合局部退化序列的基线；
- Transformer 用投影、正弦位置编码和自注意力建模窗口内全局依赖；
- 同时实现两者的意义是建立可复现对照，不是预设 Transformer 必然更优。

当前两者都只有两层，规模分别约 5.8 万和 7.1 万参数，适合单机 CPU 演示。更复杂网络
应当建立在数据、验证和发布闭环稳定之后，而不是为了模型名称堆叠复杂度。

### 6.8 “在线训练”到底是什么意思

当前“在线”表示：用户可在 Doro 中按需提交任务、查询进度，并在发布后立即通过
`version=active` 使用新模型。它不表示实时接收传感器、不表示每到一条样本就更新权重，
也不表示流式持续学习。当前数据来源仍是静态 FD001 文件。

## 七、模型结果及其正确使用方式

### 7.1 当前 v1 产物

| 模型 | 参数量 | 完成 epoch | 测试 RMSE | 测试 MAE | 测试 NASA Score | CPU 训练记录 |
|---|---:|---:|---:|---:|---:|---:|
| LSTM v1 | 57,665 | 9/20 | 15.1598 | 11.4221 | 446.10 | 28.68 秒 |
| Transformer v1 | 70,593 | 10/20 | 15.4443 | 11.8937 | 432.39 | 31.13 秒 |

这些值来自仓库现有 `artifacts/*/v1/metrics.json` 和 `config.json`。它们不是每次运行
单元测试都会重新训练得到的结果，也不能外推为真实航空发动机上的生产效果。

### 7.2 如何解释指标

- **MAE**：平均绝对误差，容易直观说明“平均差多少个周期”；
- **RMSE**：对大误差更敏感，适合强调少数严重偏差；
- **NASA Score**：非对称惩罚，高估 RUL 的代价增长更快，因为延后维护通常风险更高。

模型选择应优先看验证集，不应反复使用官方测试集挑版本。当前结果也说明没有单一模型
在所有指标上全面领先，因此简历中应报告事实，不使用“显著优于”“全面领先”等措辞。

### 7.3 测试数字的来源

```powershell
# Doro 主项目
uv run pytest -q

# PHM 独立环境
uv run --project extensions/phm pytest -q extensions/phm/tests
```

当前结果分别为 `234 passed` 和 `32 passed`。它们是两套独立环境、独立收集范围，
不是一次 pytest 运行得到的 266 项单体测试。

主项目测试覆盖 Agent、CLI、MCP stdio/HTTP、权限、会话、Skill、子 Agent、状态 UI、
用量和价格等；真实模型 Provider 使用 Mock，不消耗 API Key。PHM 测试使用合成数组、
临时 SQLite 和一轮微型 CPU LSTM 训练，覆盖数据、模型、任务、Worker、MCP、候选发布、
推理和回滚，但不等于完整复训 FD001、真实网络/GPU 测试或长期后台压力测试。

## 八、面试表达

### 8.1 一句话版本

> Doro 是一个同时面向软件工程和工业健康管理的本地智能体，通过 Tool Calling、Skill
> 与 MCP 统一编排 Coding 工具、确定性时序模型和异步训练生命周期。

### 8.2 30 秒版本

> 我基于 Python Agent 重构并扩展了 Doro。它支持两类 LLM 后端、Tool Calling、权限、
> 会话、Skill 和 MCP，能执行代码搜索、修改、Shell/Git 和测试。为了验证底座不只会
> Coding，我接入了 C-MAPSS PHM：LLM 负责理解和编排，本地 LSTM/Transformer 负责
> RUL 数值，SQLite 与独立 Worker 负责异步训练，模型先进入候选区，检查后才能发布并
> 支持回滚。项目分别通过 234 项主测试和 32 项 PHM 测试。

### 8.3 两分钟 STAR 版本

**Situation：** 通用 Coding Agent 能操作代码，但直接让 LLM 计算工业设备寿命会产生
数值幻觉；把 PyTorch 训练塞进同步工具调用，又会导致阻塞、超时和权限混乱。

**Task：** 在不侵入 Agent 主循环的前提下，让同一运行时既能完成仓库级 Coding，
也能安全编排数据预处理、RUL 推理、异步训练和模型发布。

**Action：** 我先统一了 Tool Calling、5 种权限模式、Skill、MCP、会话和上下文管理；
随后为 FD001 实现设备级切分、训练集独立标准化、30 周期窗口和两种轻量模型；再把
6 个读取能力与 10 个管理能力拆成两个 MCP Server，以 SQLite 和带租约/心跳的 Worker
执行训练，并用候选区、五项产物校验、活动版本注册和回滚管理模型生命周期。

**Result：** Doro 能在一个对话入口中完成 Coding 和 PHM 两条可验证链路；现有 v1
LSTM 在 100 台官方测试发动机上达到 RMSE 15.16，Transformer 的 NASA Score 为
432.39；主项目 234 项和 PHM 32 项测试通过。更重要的是，模型数值、训练状态与发布
状态都来自确定性系统，而不是 LLM 的文字声明。

## 九、高频面试追问与参考回答

### 9.1 为什么不拆成两个项目？

因为两条工作流共用 Agent 循环、权限、Skill、MCP、会话和执行反馈。PHM 的价值是
验证这套通用底座能处理重型依赖、长任务和模型状态，而不是再展示一个孤立算法脚本。

### 9.2 PHM 为什么需要 LLM？

模型计算不需要 LLM。LLM 的价值是把自然语言映射为设备、模型和操作，组织质检、预测、
比较与解释，并披露安全边界；RUL 必须由 PyTorch 模型输出。

### 9.3 MCP 相比直接 import 有什么实际收益？

它把 PyTorch 环境、JSON Schema、进程生命周期、超时、错误和权限从 Agent 核心中
分离。代价是增加子进程和协议调试成本，因此项目同时实现 `/mcp`、`/doctor`、连接
状态和超时错误，不能只讲扩展性而忽略运维复杂度。

### 9.4 `readOnly: true` 能保证工具绝对安全吗？

不能。它是配置方对 Server 的信任声明，Doro 用它决定 plan 模式准入和并发执行。
真正的安全还依赖服务端不实现副作用、写服务单独配置以及操作系统和目录权限。

### 9.5 没写超参数时为什么要先确认预设？

训练会占用时间和计算资源。Skill 会先展示 standard 预设的完整参数，用户同意后才以
`preset_confirmed=true` 提交；如果用户提供部分参数，其余值由所选预设补齐并在结果中
说明来源。这避免 Agent 在用户不知道预算时直接启动训练。

### 9.6 Agent 关闭后 queued 任务会怎样？

任务保存在 SQLite，不会随对话消失。后台 Worker 如果仍在运行会继续处理；如果没有
Worker，后续调用 `ensure_training_worker` 或启动管理流程后会继续领取 queued 任务。

### 9.7 当前 Worker 能并行训练多个任务吗？

不能。当前是单机、全局单实例租约，任务按创建时间顺序领取。租约和心跳已解决重复
启动与状态可见性，但真正多 Worker 仍需任务级租约、资源调度、失败重试和孤儿恢复。

### 9.8 如何避免数据泄漏？

先按发动机 ID 切分，再只用训练发动机拟合特征选择和标准化器，最后分别生成窗口。
不能先把高度重叠的窗口混在一起随机切分。

### 9.9 为什么 RUL 截断为 125？

早期寿命阶段通常没有明显退化信号，线性的大 RUL 标签会让模型过度拟合难以区分的
早期区间。截断是建模假设，用于控制损失分布，不是航空发动机的物理寿命上限。

### 9.10 为什么不自动发布验证指标最好的候选？

指标只是门禁的一部分，还要核对数据版本、参数、产物完整性、是否为 smoke 任务和
回归结果。当前保留人工确认；生产化应进一步把阈值、审批身份和审计记录下沉到服务端。

### 9.11 退化趋势证据是不是根因分析？

不是。当前只返回最后窗口内标准化变化幅度和斜率较强的特征，是描述性证据。根因诊断
还需要传感器—部件映射、机理知识、消融实验和真实故障标签。

### 9.12 当前项目最大的限制是什么？

- FD001 是单工况、单故障模式的仿真数据，不代表真实生产分布；
- 当前本机 v1 是 CPU 训练记录，CUDA/MPS 路径未在本次验证中实测；
- 单机单 Worker，不是分布式训练平台，也不支持 checkpoint 续训；
- 没有 Web 管理控制台、自动指标门禁和服务端审批令牌；
- 经验残差区间不是具有严格覆盖保证的概率置信区间；
- 不接实时传感器，也不进行样本级持续学习。

## 十、8 分钟现场演示脚本

### 10.1 第 1 分钟：证明这是统一 Agent

```text
/status
/mcp tools
/skills
```

指出 Coding 工具、`phm` 6 个只读工具、`phm-admin` 10 个管理工具和两个 PHM Skill。

### 10.2 第 2～3 分钟：演示 Coding 闭环

选择一个可恢复的小修改：读取文件、搜索调用位置、修改、运行定向测试、展示 Git diff。
重点展示每一步都有真实工具结果，而不是让模型生成一段没有落盘的代码。

### 10.3 第 4～5 分钟：演示只读 PHM

```text
/phm 检查 FD001 测试发动机 42 的数据质量，然后比较活动 LSTM 与 Transformer，
报告预测、经验区间、模型版本和验证指标，不要改变任何状态。
```

解释预测来自模型，Agent 只组织字段；经验区间来自验证残差分位数，不是安全承诺。

### 10.4 第 6～7 分钟：演示异步训练控制面

```text
/phm-training 查看 Worker、队列和最近任务，不要改变状态。
/phm-training 训练一个 LSTM smoke 候选，版本 demo-smoke；先展示参数并等待确认，
不要发布。
```

展示预设确认、job ID、queued/running 区分、Worker PID/心跳和 epoch 进度。面试现场
不需要等待完整 standard 训练，smoke 的目的只是验证链路。

### 10.5 第 8 分钟：讲发布边界

打开一个已经 succeeded 的候选，展示指标与五项产物，但不要为了演示随意发布。说明
正式发布需要用户明确决定，活动版本更新后只读推理会通过 `active` 别名使用新版本；
异常时可回滚到上一活动版本。

## 十一、哪些数字能写，哪些不能写

### 11.1 可以写的已验证数字

- 2 类 LLM 后端、2 类 MCP 传输、5 种权限模式；
- 6 个只读 PHM 工具、10 个管理工具；
- FD001 100 台训练发动机、100 台测试发动机；
- 80/20 设备级切分、30 周期窗口、RUL 上限 125；
- 2 种模型、57,665/70,593 参数；
- v1 模型产物中记录的 RMSE、MAE、NASA Score；
- 234 项主项目测试、32 项 PHM 测试；
- Worker 默认 5 秒心跳、300 秒空闲退出；
- 发布前校验 5 项模型产物。

### 11.2 不能凭空写的内容

- 生产用户数、收入、人效提升或维护成本下降；
- 真实航空发动机部署、故障预警或维修决策效果；
- 没有专门评测过的 Coding 成功率、延迟或 Token 节省；
- 多租户、分布式 Worker、Web 控制台和自动审批；
- CUDA/MPS 训练速度或相对 CPU 加速比；
- 将单元测试通过数描述为“项目准确率”或“线上稳定性”。

如果简历必须强调影响，可以先补充可复现评测，而不是估算漂亮数字：Coding 任务成功
率、平均工具轮次、只读并发收益、同步/异步提交延迟、CPU/GPU 训练耗时、推理 P50/P95、
Worker 故障恢复时间以及 PHM 工具选择正确率。

## 十三、后续演进路线

建议按“先补评测和工程门禁，再扩算法”的顺序推进。

### P0：让当前项目更可测、更可演示

1. 建立 Doro Coding + PHM 任务评测集，记录成功率、工具选择、越权率和完整性；
2. 增加训练队列、loss 曲线、活动版本和回滚历史 Web 仪表盘；
3. 为发布加入验证指标阈值、数据哈希、回归测试和 smoke 推理门禁；
4. 接入 MLflow 或自建实验追踪，关联参数、Git SHA、manifest、曲线与产物。

### P1：增强可靠性和资源治理

1. 增加 checkpoint 续训、有限重试、超时、磁盘配额和候选清理；
2. 从全局单实例租约演进到任务级租约、多 Worker 资源调度和孤儿恢复；
3. 增加操作者身份、服务端审批令牌、不可变事件日志和模型签名；
4. 测量 MCP/推理 P50、P95 延迟及 Worker 冷启动、故障恢复时间。

### P2：扩展工业算法深度

1. 支持静态 CSV/NPZ 上传、字段映射、批量质检与异步预测；
2. 扩展 FD002～FD004，多工况归一化并报告跨子集泛化；
3. 引入 XGBoost、TCN 等基线，比较精度、参数量、CPU 延迟和维护成本；
4. 将经验残差区间升级为 split conformal prediction，并监控覆盖率；
5. 增加数据漂移、OOD 检测、传感器消融和 Integrated Gradients，同时保持
   “统计证据不等于物理因果”的边界。
