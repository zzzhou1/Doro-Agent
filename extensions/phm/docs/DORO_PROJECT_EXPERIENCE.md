# Doro：可 Coding、可 PHM 的统一智能体项目经历与面试指南

## 一、项目定位结论

这个仓库不应被描述成两个互不相关的项目：一个 Coding Agent，加一个 C-MAPSS
预测脚本。更准确、也更有竞争力的定位是：

> Doro 是一个可扩展的本地智能体平台。它以统一的 Agent 循环、工具调用、权限、
> Skill、MCP、会话与上下文系统为底座，同时支持软件工程 Coding 工作流和工业装备
> PHM 工作流；在 Coding 场景中操作代码、终端与 Git，在 PHM 场景中编排确定性的
> 时序模型、异步训练任务和模型生命周期。

产品、Python 包、CLI、环境变量前缀、用户数据目录和 MCP 服务标识已经统一为
`Doro` / `doro`，简历、作品集、终端演示与源码使用同一套名称。

## 二、为什么这是融合，而不是简单拼接

Coding 与 PHM 共用同一套 Agent 核心：

```text
                         ┌─ 文件、搜索、Shell、Web、Git ─→ Coding
用户 → LLM Agent 循环 ──┤
                         └─ Skill → MCP → 时序模型/训练队列 ─→ PHM
          │
          ├─ OpenAI-compatible / Anthropic 后端
          ├─ 流式输出与多轮工具调用
          ├─ 权限模式与危险操作确认
          ├─ 会话恢复、记忆、上下文压缩
          ├─ 子 Agent 任务委派
          └─ 项目级/用户级配置发现
```

两类场景的共同问题都是：自然语言模型不应该直接假装完成确定性工作。

- Coding 任务必须由文件、搜索、Shell 和 Git 工具实际执行；
- RUL 数值必须由本地 LSTM/Transformer 实际计算；
- 训练必须由队列与 Worker 执行，不能让 LLM 假装“已经训练”；
- 发布和回滚必须改变可审计的模型注册表，不能只在对话中宣称完成；
- 权限系统必须区分读取、修改、执行和发布等不同风险操作。

因此，PHM 不是挂在 Doro 旁边的演示脚本，而是验证 Doro 能否从通用 Coding 扩展到
专业工业工作流的一套垂直能力。

## 三、统一架构应该怎样讲

### 3.1 Agent 核心层

Doro 的核心负责：

- 支持 Anthropic 与 OpenAI-compatible 模型后端；
- 维护流式、多轮的工具调用循环；
- 加载项目规则、用户规则和环境配置；
- 管理普通、计划、自动接受编辑等权限模式；
- 发现并调用本地 Skills；
- 连接 stdio 与 HTTP/SSE MCP Server；
- 保存与恢复会话；
- 管理长期记忆和上下文压缩；
- 支持子 Agent 执行独立任务；
- 展示模型、上下文、费用与 MCP 状态。

### 3.2 Coding 能力层

Coding 工作流由确定性工具完成：

- 阅读和修改项目文件；
- 搜索符号、调用链和配置；
- 运行 Shell 命令、测试、构建和静态检查；
- 执行 Git 状态检查、差异审阅和提交；
- 在权限约束下完成多轮“理解—修改—验证—交付”。

这一层体现的是通用软件工程 Agent 能力。

### 3.3 PHM 能力层

PHM 工作流通过独立 Python 包、MCP 和 Skills 接入：

- 对 NASA C-MAPSS FD001 进行可信下载与哈希校验；
- 按发动机划分训练/验证，完成标准化和时序窗口生成；
- 使用 LSTM 与 Transformer 进行 RUL 回归；
- 将质检、预测、比较、指标和趋势证据封装成只读 MCP；
- 将提交训练、查询进度、取消、发布和回滚封装成写管理 MCP；
- 使用 SQLite 保存训练任务、参数来源和 Worker 租约/心跳；
- 按需隐藏启动或复用独立 Worker，在 CPU/CUDA/MPS 上运行训练并空闲退出；
- 使用候选区、活动版本注册表、原子发布和回滚管理模型生命周期。

这一层体现的是工业算法与 Agent 工程的融合，而不只是模型训练。

### 3.4 权限和执行边界

统一平台不等于所有工具都拥有相同权限：

| 能力 | 执行主体 | 权限特点 |
|---|---|---|
| 读取代码和模型指标 | Coding 工具或只读 PHM MCP | 可并行、低风险 |
| 修改代码 | Coding 编辑工具 | 需要编辑权限和差异审阅 |
| 运行命令与测试 | Shell 工具 | 受命令权限约束 |
| 提交训练 | `phm-admin` MCP | 写队列，但不立即改变活动模型 |
| 执行训练 | `phm-worker` | 独立进程和资源边界 |
| 发布/回滚 | `phm-admin` MCP | 改变活动模型，要求明确确认 |
| RUL 推理 | `phm` MCP | 只读、确定性模型输出 |

这种分层是项目的重要设计点：同一个 Agent 可以 Coding 和 PHM，但不同能力仍然保持
最小权限和清晰的责任边界。

- 通过依赖锁、配置优先级、超时、错误回传和 Git 工作流增强可复现性与工程可靠性。

### 7.3 工业智能 / 算法工程岗

- 构建设备级切分、标准化、时序滑窗、RUL 标签与评估链路，避免相邻窗口跨训练/验证

- 将数值预测封装为确定性 MCP 工具，由 Doro 负责问题理解、质检顺序、模型选择与
  结果解释，保持 LLM 推理和算法计算的责任分离；
- 实现可查询、可取消、可发布、可回滚的训练任务与模型版本系统，使算法实验具备面向
  Agent 应用所需的生命周期管理。

## 十、常见面试追问

### 10.1 为什么不把 Coding Agent 和 PHM 拆成两个项目？

因为它们共用 Agent 循环、权限、Skill、MCP、会话和执行反馈。PHM 的意义正是验证
这个底座能否扩展到专业场景。拆开描述会丢掉最有价值的“通用平台 + 垂直能力”设计。

### 10.2 PHM 为什么需要 LLM？

LSTM/Transformer 负责数值计算，不需要 LLM。LLM 的价值是理解自然语言需求、选择
正确工具、执行先质检后推理的流程、组合模型指标和退化证据，并清楚说明结果边界。

### 10.3 为什么使用 MCP，而不是直接在 Agent 中 import 模型？

MCP 将能力、输入 Schema、进程依赖和权限边界独立出来。PHM 可以使用单独 PyTorch
环境，Agent 主程序不需要安装重型模型依赖；同一模型服务也能被其他 MCP 客户端复用。

### 10.4 为什么训练需要独立 Worker？

模型训练耗时长、资源占用高，直接放在 MCP 请求里会导致超时并阻塞对话。管理 MCP
只做校验和入队，Worker 负责计算，Agent 可以退出后重新查询持久化任务状态。

### 10.5 为什么不训练完成后自动发布？

训练完成只代表有产物，不代表质量满足上线条件。候选还应检查验证表现、数据版本和
回归结果，因此发布需要显式确认，并保留上一活动版本用于回滚。

### 10.6 为什么拆成只读和写管理 MCP？

如果预测和发布在同一个写 Server 中，普通查询也无法获得清晰的只读身份。拆分后，
预测可以安全并行和用于计划模式，训练、发布与回滚则保留独立权限和审计边界。

### 10.7 “在线训练”是否等于实时传感器或持续学习？

不是。当前实现是对静态 FD001 的按需异步训练和在线任务控制，不接实时传感器，也不
做样本级持续更新。这样描述更准确，也与当前代码一致。

### 10.8 项目目前最大的限制是什么？

- PHM 数据是仿真 FD001，不代表真实生产分布；
- 当前是单机单实例 Worker，不是分布式训练平台；
- 模型发布需要人工检查，但还没有完整的自动门禁与审批服务；
- 当前 Web/UI 展示有限，主要通过终端和 Agent 对话交互；
- 当前没有 Web 管理控制台，训练与模型生命周期主要通过 Doro 对话和 CLI 管理。

主动说明这些限制不会削弱项目，反而能体现你清楚原型、工程系统和生产平台之间的
差距。

## 十一、可以量化什么，不应该编造什么

用户明确不希望被旧简历指标束缚，这是合理的。简历不一定要用模型精度做主结果；可以
量化当前实现中可验证的系统范围，例如：

- 支持的模型后端、工具类别和领域工作流；
- 只读推理与写管理两类权限平面；
- LSTM/Transformer 两类时序模型；
- CPU/CUDA/MPS 三类设备后端；
- 任务提交、查询、取消、发布、回滚等生命周期阶段；
- 自动化测试、构建和真实 smoke 流程。

但不要编造：

- 生产用户数、业务收入或人效提升；
- 真实航空发动机部署或维修决策；
- 没有测量过的 Coding 成功率和端到端效率提升；
- 当前没有实现的多租户、分布式 Worker、Web 控制台或自动审批；
- 把来源于旧 Doro 底层的指标迁移到这个新实现。

如果后续希望加入更强的结果指标，建议新增一套 Doro 自身的评测，而不是借用旧项目：

1. 设计一组仓库级 Coding 任务，统计正确修改率、测试通过率和平均工具轮次；
2. 设计 PHM 工作流任务，统计工具选择正确率、越权发布率和结果字段完整率；
3. 测量直接同步训练与异步入队的响应时间差异；
4. 测量 CPU/GPU 训练耗时、推理延迟和模型加载缓存收益；
5. 对权限模式、MCP 超时和失败恢复开展故障注入测试。

这些数据来自当前 Doro 底层，未来写进简历会比沿用旧项目数字更可信。

## 十三、推荐演示顺序

面试现场可以用同一个 Doro 进程演示两条链路：

```text
Coding：读取仓库 → 搜索调用链 → 小范围修改 → 运行测试 → 展示 Git diff
PHM：检查 MCP → 查询活动模型 → 检查发动机 → RUL 预测/比较 → 解释边界
训练：提交候选 → 查看 epoch 进度 → 检查指标 → 明确确认 → 发布/回滚
```

演示重点不是让面试官等待完整模型训练，而是展示：统一 Agent 如何选择工具、权限如何
变化、任务如何持久化、数值从哪里产生、模型为什么不能自动发布。

## 十四、后续演进方向

优先级建议：

1. 建立 Doro 自身的 Coding + PHM 任务评测集；
2. 增加训练任务和模型版本 Web 仪表盘；
3. 为候选发布增加指标阈值、回归测试和审批门禁；
4. 接入 MLflow 或自建实验追踪；
5. 支持用户上传静态工业时序文件进行批量质检和预测；
6. 增加训练 checkpoint 恢复、失败重试和多 Worker 资源调度；
7. 扩展 FD002～FD004 多工况与多故障模式；
8. 增加 conformal prediction、漂移监控和覆盖率评估；
9. 为 Doro 配置、会话和训练审计记录增加导出、导入与备份工具；
10. 将 Coding 和 PHM 的执行轨迹统一沉淀为可审计事件流。

这些方向能够继续强化“通用 Agent 平台 + 工业垂直能力”，而不是堆叠更多互不关联的
小功能。
